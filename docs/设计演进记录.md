## 一句话定位

跨境电商购物 Agent。买家一句自然语言诉求，Agent 自己完成品类洞察、商品检索、
到手价计算、经买家确认后创建本地订单，过程通过官方 AG-UI 客户端与 POST/SSE 实时可见；WebSocket 保留为兼容路径。

## 分期交付

### 一期：MVP 骨架

- MainAgent（总管，持有全部业务工具可单干）+ SearchAgent + TradeAgent
- 商品检索、订单创建/查询/取消、内存仓储 + 10 条种子商品
- FastAPI + WebSocket 事件流（8 类事件）、TradeEventBus 按会话路由
- 交付：23 单测绿，真实 LLM 三轮冒烟通过

关键取舍：**SubAgent as Tool**。2.0 库级没有 subagent 原语（官方 Agent Team 只在
`agentscope.app` 平台层，需要 storage/message_bus/workspace 全套），因此用
`FunctionTool` 包装 `task_dispatch(subagent_type, demands)` 实现同等语义。
否决了引入整个 app 平台层——那会把自建的 FastAPI/WS/EventBus 全部推翻。

### 二期：检索与计价

- 二阶段召回：embedding（text-embedding-v4, dim=1024）→ Qdrant COSINE → HTTP Reranker
- 降级链 `embedding_rerank → embedding_only → keyword_2gram`，`recall_strategy` 如实标注
- 到手价内联：汇率表 + 关税规则（免税额度 / 品类费率 / 续件运费）
- 长期记忆（跨会话偏好）+ 会话 AgentState 落盘恢复
- 评测回归 10 case + TracingMiddleware + Docker Compose
- 交付：47 单测绿，评测 10/10 PASS 均分 0.965

关键取舍：**价格计算收敛进检索工具**。不给 Agent 单独的比价工具和运费工具，
到手价在检索链路内联算好随商品卡返回。理由是每多一个工具就多一轮模型调用，
而价格是检索结果的固有属性，没有单独查询的必要。

### 三期：知识、上下文、并行、韧性、前端

- 品类洞察 RAG：`category_insight_tool` 查 `rag.KnowledgeBase`（5 篇知识文档 / 9 chunks）
- 上下文压缩：`ContextConfig(trigger_ratio=0.75, reserve_ratio=0.15)`，摘要落 `AgentState.summary`，发 `context.compressed` 事件
- 真并行 fork：`task_dispatch` 标 `is_concurrency_safe=True`，走 2.0 并发批执行
- 工具韧性：`ToolResilienceMiddleware` 分级超时 + 按工具熔断（closed→open→half_open）
- React + Vite 前端：对话流 + 商品卡 + 事件时间线
- 交付：64 单测绿，评测 13/13 PASS 均分 0.988，并行实测 **1.84x** 加速（wall 20.6s vs 串行 38.0s）

关键取舍：**硬约束过滤要可观测**。结构化过滤（价格上限 / 可达国）原先静默丢弃候选，
模型只看到剩下的 hits，无法区分"库里没有"与"被我自己的约束挡掉了"。
补 `filtered_out`（含 reason）后模型才能如实说"有但超预算"。详见踩坑档案第 6 条。

### 四期：工程基建

- **配额治理**：`GatewayThrottle` 并发上限 + 请求起点间隔双约束；限流重试用尽后回退备用模型并发 `model.fallback`
- **持久化**：SQLite（SQLAlchemy 2.0 async）存对话流水 / 事件轨迹 / 会话状态 / 订单 / 偏好
- **缓存**：Redis 语义缓存（命中零模型调用）+ embedding 缓存 + 幂等键
- **削峰**：Redis Stream 队列 + 独立 worker 进程（ack / pending 重投 / 死信 / 优雅退出）
- 交付：137 单测绿；真实验证含落库查库、跳重启恢复、语义缓存 8.8s→3.0s、跨进程事件直达前端

关键取舍：

1. **同步接口契约不变**。`POST /commerce/intents` 内部改成入队 + 等结果，而不是改成纯异步——
   13 case 评测与前端都依赖它直接返回 `final_text`。削峰靠的是 worker 并发度，与接口形态无关。
2. **闸门共享 + 并发数取 2**。三个 Agent 工厂各建模型实例但共用一个 `GatewayThrottle`，
   否则各限 2 就变成实际 6 并发；不取 1 是为了保住三期 1.84x 的并行收益。
3. **中间件全可关**。`DATABASE_URL=file` / `REDIS_URL=` / `QUEUE_ENABLED=0` 三个开关全关时
   退回三期行为，已实测业务结果一致。现有单测不依赖任何外部中间件。
4. **不做 MySQL**。SQLite 已满足当前需求；不装驱动就不声称支持，避免“看上去支持其实未验证”。
   仅保留换驱动的路径（换 `DATABASE_URL` + 装异步驱动）。

## 踩坑档案

按"现象 → 根因 → 修法 → 可复用教训"记录，只收有复用价值的。

**1. pydantic schema 生成崩溃**
现象：工具注册即报 `_StructuredOutputDynamicClass is not fully defined`。
根因：工具模块用了 `from __future__ import annotations`，注解变字符串，
AgentScope 从函数签名动态生成 JSON schema 时解析失败。
修法：工具模块一律不加该导入，并在文件头注释说明原因。
教训：靠运行时反射读注解的框架，与 PEP 563 延迟注解天然冲突。

**2. 上下文压缩抛 KeyError**
现象：触发压缩时报 `KeyError: 'summary'`。
根因：自定义 `summary_template` 的占位符必须与 2.0 的 `summary_schema` 五个字段
（`task_overview` / `current_state` / `important_discoveries` / `next_steps` / `context_to_preserve`）
严格对齐，写错一个就崩。
修法：占位符改齐五字段，并加渲染单测防回归。
教训：框架提供的模板扩展点，占位符集合是硬契约，必须查实际 schema 而不是凭直觉命名。

**3. 前端商品卡永远渲染不出**
现象：接口返回正常，前端商品卡区域一片空白。
根因：`tool.result` 事件只带了 `hit_count` 没带 `hits`，前端无数据可渲染。
修法：事件补 `hits`，并加确定性单测锁定"事件必须携带商品卡"。
教训：这个缺陷单测和接口测试都发现不了，只有真开浏览器才暴露。端到端可视验证不能省。

**4. 2.0 权限模式下写工具挂起**
现象：调用下单工具后 Agent 回 `I'm waiting for your permission...` 然后卡住。
根因：2.0 的 DEFAULT 权限模式会对写操作类工具要求人工确认。
修法：新增 `permissions.py`，对业务写工具/Task/调度/记忆工具精准 allow，
不用 BYPASS 全放开。
教训：框架的安全默认值要精准放开而不是一把关掉。

**5. Qdrant 本地嵌入模式文件锁冲突**
现象：服务启动报存储被占用。
根因：qdrant-client 本地嵌入模式是单进程文件锁，残留的 uvicorn 进程仍持锁。
修法：本地开发注意清理残留进程；生产用 compose 的 Qdrant 服务端。README 标注。
教训：嵌入式存储不能用于多进程/多实例，四期引入 worker 进程后更要注意。

**6. 硬约束过滤导致误导性回答**
现象：多轮对话里买家问登山杖，Agent 答"没有找到专门的登山杖产品"，
但商品库明确有 P1010 CascadePro（149 USD）。
根因两层：一是模型把第 1 轮的"300 元以内"预算沿用到了换品类后的第 3 轮；
二是检索的价格硬过滤静默丢弃候选，模型无从区分"库里没有"和"被过滤了"。
修法：检索返回加 `filtered_out`（含 `over_price_cap` / `ship_to_unavailable` + 目标币种价格）；
prompt 补两条——约束不跨轮沿用、`filtered_out` 里有目标品类必须如实说明。
教训：**给模型的工具返回值要能自证边界**。只返回"筛选后的结果"会让模型把
过滤动作误读成客观事实，进而产生自信的错误陈述。

**7. 评测夹具误判正确行为**
现象：跨会话记忆 case 被 judge 判 FAIL，理由"无依据添加偏好"，
但 Agent 实际正确应用了上一个 case 写入的长期偏好。
根因：judge 只收到本会话的 transcript，看不见跨会话写入的事实。
修法：case 支持 `prior_context` 字段，把已成立的前置事实告知 judge。
教训：评测失败先分清"被测系统错"还是"评测夹具错"，否则会把正确实现改坏。

**8. 网关限流是间歇的，不由自己的并发量决定**
现象：探测 `qwen3.7-plus` 时，**单发一条请求**也返回
`429 Throttling.Concurrency`，耗时 47 秒；次日同样的单发请求却正常返回。
根因：配额池共享，限流与本客户端并发量无关，取决于当时全局用量。
修法：客户端限并发 + 平滑爬升 + 指数退避，并配备用模型自动回退。
教训：共享配额池的限流既不可控也不可复现，只做客户端限流不够，必须有降级路径；
反过来也不能把一次探测结果当成模型的固定结论。

**9. 事件总线拆进程后会断链**
现象：把意图处理移到独立 worker 进程后，前端拿不到 `token.delta` 与工具事件。
根因：`TradeEventBus` 是纯进程内 asyncio 总线，worker 产生的事件推不到 API 进程的 WS。
修法：加 Redis Pub/Sub 背板，API 进程订阅后 `deliver_local` 转发；publish 保持同步签名，
广播走 fire-and-forget 任务（任务得挂强引用，否则可能完成前被 GC）。
教训：拆进程前先盘点所有进程内共享状态（总线、内存缓存、信号量），它们都会默默失效。

**10. Pub/Sub 不排除发布者，导致事件回环**
现象：接背板后前端每条事件收到两次（实测：`task.queued` 计数 2）。
根因：API 进程既发布又订阅同一频道，Redis 会把消息送回给发布者，于是本地投递 + 背板转发各一次。
修法：广播消息包上 `origin`（进程唯一标识），订阅端跳过自己发的，并加测试锁住。
教训：发布订阅做广播背板时，“自己会收到自己”是默认行为，必须显式去重。

**11. 可选依赖被当成 dev 依赖，容器直接起不来**
现象：本地单测全绿，容器启动报 `ModuleNotFoundError: aiosqlite`。
根因：`uv add --dev aiosqlite`，但 SQLite 已是默认存储，属于运行时必需。
修法：改为生产依赖。
教训：“默认路径上用到的东西”一定是生产依赖；这类错误单测永远拓不到，只有真起容器才暴露。

**12. 连接池参数不能跳驱动沿用**
现象：把服务型数据库的 `pool_size` / `pool_recycle` 给 SQLite 会报错或无意义。
修法：`create_engine` 按驱动分支；SQLite 额外开 WAL 与 `busy_timeout`，
缓解 worker 与 API 双进程写同一文件时的锁竞争。
教训：同一层 ORM 下不同驱动的运维参数不可互换，必须显式分开。

**13. 语义缓存把评测弄成了“评缓存”**
现象：一条 case 失败（Agent 只给选购建议不给商品，还编了句“检索工具有技术限制”）；
改完 prompt 重跑，回复**一字不差**，连那句编的话都一样。
根因：那条错回复进了语义缓存（内容有问题但不以 [error] 开头，没被过滤掉），
TTL 24h 内相同提问全部复用；评测因此完全失去检验能力。
修法两层：
  1. 缓存 key 带上模型名 + 提示词文件指纹，prompt 一改旧缓存自动作废；
  2. 评测脚本开跑前查 `/health`，语义缓存开着就直接拒跑（需 `--allow-semantic-cache` 才能绕过）。
关掉缓存重跑后同一条 case 得 1.0——Agent 行为本来就是对的。
教训：任何带缓存的链路上做质量评测，都必须先确认缓存已关；
否则你以为在测模型，实际在测 Redis。反过来，缓存 key 也应该把“影响输出的配置”全部纳入指纹。

## 当前状态与已知边界

- `recall_strategy` 实际停在 `embedding_only`：未部署 reranker 服务，走的是设计好的
  降级链而非故障。要跑满二阶段需配 `RERANKER_BASE_URL`。
- 评测分数与所用模型绑定：0.988 是 qwen-plus 的成绩，换模型需重跑并在报告标注。
- 网关配额是长期约束，且限流具有间歇性（同一模型同样的单发请求，不同时间结果不同）；
  四期的闸门与回退是应对手段，不是根治。
- 商品目录仍是种子数据 + 内存仓储，未落库（四期有意不做，避免牵动向量建库与
  评测 ground truth 构造）。
- 回退链（`model.fallback`）**只有单测证据**：真实网关限流间歇发生，本期未能主动复现。
- SQLite 单写者：worker 与 API 双进程写同一文件，已开 WAL + busy_timeout 缓解，
  但高并发仍应换服务型数据库。
- 语义缓存只覆盖首轮、非写操作、同买家的问句；这是有意收紧的安全边界，不是能力缺失。

## 换实现的方法

洋葱架构下替换基础设施只需两步：在 `app/domain/**/ports/` 找到（或补上）端口定义，
在 `app/infrastructure/` 加实现，然后改 `app/composition.py` 的装配接线
（四期把组装根从 `server.py` 抽了出来，API 与 worker 两个进程共用一份接线，
避免两处各 new 一套导致行为漂移）。
`application` 与 `domain` 不需要改动。

四期已按此方式完成的替换：文件存储 → SQLite（`SessionStore` / `ConversationStore` /
`OrderRepository` / `PreferenceStore` 四个端口）、进程内直跑 → Redis Stream 队列（`TaskQueue` 端口）。
同理可换 RabbitMQ（实现 `TaskQueue`）、PostgreSQL（换 `DATABASE_URL` + 装 asyncpg）。
